# Step 6: Power BI — YouWe CRM SaaS Dataset

## The star schema

```
dim_customer ──┐
dim_plan ──────┼──< fact_monthly_subscription  (drives MRR trend, sliceable by any dimension)
               │
               ├──< fact_mrr_waterfall          (pre-classified new/expansion/contraction)
               ├──< fact_churn_by_month         (monthly churn rate, already excludes the
               │                                 uncomputable final month — see below)
               ├──< fact_cohort_retention       (feeds the cohort heatmap directly)
               └──< fact_customer_clv           (one row per customer — CLV, segments, channel)
```

Every fact table above was generated by a **validated SQL query already tested against your live database** (not written blind) — see `powerbi_queries.sql` for the full, commented queries and their row counts.

## A real methodology fix baked into this step

STEP5_README.md flagged an inconsistency between Step 3's Query 2 and Query 3 (two different definitions of "active this month"). This step resolves it: every fact table here uses **one single, consistent definition** — a subscription counts as active in a month if it started on or before that month's 1st. This is a good thing to mention in an interview: not just that you noticed an inconsistency, but that you went back and fixed the data layer so the dashboard doesn't inherit it.

## A second real bug caught before it reached the dashboard

The first version of `fact_churn_by_month` showed **100% churn for December 2025** — every customer active that month, since there's no "January 2026" in the dataset to check whether they stayed. This is a known data problem called **right-censoring**: you genuinely cannot know yet whether the most recent period's customers will churn. The fix excludes the final month from churn reporting entirely — standard practice, and worth explaining if anyone asks why your churn chart stops one month before your MRR chart does.

## Install the PostgreSQL driver (Npgsql)

Power BI's PostgreSQL connector needs this installed separately — it's not bundled.

1. Go to https://github.com/npgsql/npgsql/releases
2. Find the latest release, download the `.msi` installer (look for something like `npgsql-x.x.x-x64.msi` — get the 64-bit version)
3. Run it, accept defaults
4. Restart Power BI Desktop if it was already open

## Connect Power BI to PostgreSQL

1. Open Power BI Desktop → Get Data → search "PostgreSQL" → PostgreSQL database → Connect
2. Server: `localhost:5432` (or just `localhost` if it asks for port separately)
3. Database: `youwe_crm`
4. Data Connectivity mode: **Import** (not DirectQuery — this dataset is small enough that Import gives better performance and lets you work offline)
5. It'll ask for credentials the first time — Database → username `postgres`, the password you set back in Step 3

## Import each table

Instead of picking tables from the Navigator, use a native query for each one — this way you're importing exactly the validated logic, not raw tables Power BI would need complex DAX to reshape.

For **each** of the 7 queries in `powerbi_queries.sql`:
1. Get Data → PostgreSQL database → paste `localhost:5432` and `youwe_crm` again (or if already connected, right-click in the Queries pane → New Query → Blank Query, then use Home → Advanced Editor)
2. Actually, simplest path: when you first connect, there's an "Advanced options" expander in the connection dialog — click it, and a "SQL statement" box appears. Paste **one** query's SQL into it, click OK. This becomes one table.
3. Rename the resulting table to match the name in the comment above each query (`dim_customer`, `fact_monthly_subscription`, etc.) — click the table name in Power Query Editor and rename it there before loading.
4. Repeat for all 7 queries (you'll do the "Get Data" step 7 times total, once per table — that's normal, it's not a bug).
5. Once all 7 are added in Power Query Editor, click **Close & Apply**.

## Build the relationships (this is the "star schema" part)

In Model view (left sidebar icon that looks like connected boxes):

- `dim_customer[customer_id]` → `fact_monthly_subscription[customer_id]` (one-to-many)
- `dim_customer[customer_id]` → `fact_mrr_waterfall[customer_id]` (one-to-many)
- `dim_customer[customer_id]` → `fact_churn_by_month` — **no direct relationship needed**, this table is already aggregated to month grain
- `dim_customer[customer_id]` → `fact_customer_clv[customer_id]` (one-to-one)
- `dim_plan[plan_id]` → `fact_monthly_subscription[plan_id]` (one-to-many)

Power BI usually auto-detects most of these when the column names match — check each one it creates and confirm the direction/cardinality is right rather than assuming it guessed correctly.
